# 分组开发与核心维护

## 维护责任

| 团队 | 负责范围 | 不允许直接修改 |
| --- | --- | --- |
| 核心平台 | vendor 升级、shared 契约、启动、资源、热更、编辑器工具、发布流水线 | 未评审地修改已发布协议/存档 |
| 平台接入/网络 | 微信身份/网络桥、后台前台恢复、连接状态、平台能力验证 | 业务奖励与经济规则 |
| 大世界 | World 模块、AOI 消费、分线体验、玩家走动与自动探索表现 | 确定性内核、跨服写入权 |
| 战斗 | Battle 模块、确定性系统、回放、帧输入、技能表现接口 | Unity 物理充当权威模拟 |
| 角色成长 | Player 模块、角色/装备/蛊虫/背包读模型与 UI | 从客户端发放或计算权威奖励 |
| 内容策划 | design/luban、剧情/任务/区域数据与校验规则 | 手改生成 C# / bytes |
| 美术渲染 | Rendering、URP RendererFeature、相机、资产质量与三档预算 | 私自替换全项目管线/改 SRP 包 |
| 服务端 | Identity / Gateway / Lobby / Router / World / Battle / Persistence | 用分区 ID 充当全局玩家 ID |
| QA/构建 | 回归、真机、压力、发布兼容、灰度与回滚演练 | 将 smoke 通过当作生产验收 |

目前用一个 Gameplay.HotUpdate 程序集，按目录划分责任，减少首阶段多热更 DLL 加载顺序和 AOT 泛型复杂度。团队规模扩大后，由平台组评审拆分 asmdef 和版本依赖，而不是各组自行增加热更程序集。

## 核心保护

双引擎的 `client/engine-projects.json`、两个工程的 Packages/ProjectSettings、引擎专用 asmdef、Web 开发构建门禁和 SDK 兼容发布归平台组。团结侧共享目录由初始化脚本建立，源码仍按原有模块目录负责；不要提交复制出来的第二套业务代码。平台评审与测试证据见 [双引擎开发](Dual-Engine.md) 和 [验证记录](Validation.md)。

1. GF 核心仅分发预编译 SDK，当前从参考项目固定版本包引入；不把源码暴露到日常业务目录。
2. SDK 包和 .NET DLL 的 SHA-256 记录在 `vendor/dependencies.lock.json`，架构测试检查完整性。
3. asmdef + noEngineReferences 限制依赖；静态检查拒绝 AOT → HotUpdate、共享代码 → Unity、确定性代码 → 浮点/随机/系统时间。
4. `AGENTS.md` 对后续成员和代码代理说明受保护区域与开发规则。
5. `.github/CODEOWNERS` 是团队名模板，**需要替换为真实组织团队并启用受保护分支/Required Reviews 后才有审批效果**；本地文件本身不是权限控制。
6. 接入 Git/CI 后将 `Test-Architecture`、`Test-Foundation`、Unity tests 配为必过检查。禁止直接在主干写核心或绕过检查合并。

SHA 校验用于发现意外变更，不是防恶意篡改的完整安全方案。可修改锁文件的人仍能替换包；真正的保护来自仓库权限、签名发布、审查和 CI 权限隔离。

## 变更流程

业务成员优先只改自己模块、UI 和配套表。公共字段/接口改动先提交 ADR：说明兼容范围、迁移、回滚和测试，然后由核心/服务端双重评审。SDK 升级必须整体导入版本、更新锁定与验证记录，禁止替换单个 DLL 后仍标记旧版本。

文档记录验证边界。参考工程只读；不对 `D:\Project\Unity_Project\GameFramework` 做清理、格式化或代码修复。核心问题回归参考仓库单独修复，再以新版本包进入本工程。

## 下一阶段验收

- 平台组：团结原生解释器/HybridCLR 兼容与微信网络 SDK 的真机验证。
- 服务端组：登录码交换、鉴权、大厅协议、单玩家持久化与幂等结算。
- 世界组：两客户端进入同一实例、AOI 互见、移动、好友进同线。
- 战斗组：同一数据版本下的本地/网络模拟一致、断线等待、回放复核。
- 内容组：一个原创章节的数据结构与从策划表到资源包的验证流程。
- 渲染组：低/中/高档真机基准及一套角色/技能样板。
